PRISM

The privacy and context-minimization architecture used across LUMARA and SwarmSpace. This page is for developers building plugins and security reviewers evaluating the platform. PRISM is a proper noun and is not expanded as an acronym.

1. What PRISM is

PRISM is the privacy architecture that governs how user data flows through SwarmSpace and LUMARA. Its core principle: plugins receive the minimum necessary context to perform their function. Enforcement is structural wherever possible — the system is designed so that undeclared data paths are not available to plugin code, not merely disallowed by policy.

Three enforcement boundaries work together:

BoundaryRole
Manifest declaration The plugin declares required context in privacy_data_required. That list is the contract for what may ever enter the call.
Sandbox enforcement A Cloudflare Dynamic Worker V8 isolate runs the invocation. Only the declared subset is injected into the context parameter the plugin receives.
Network control globalOutbound: null (default posture) blocks all outbound network access except hostnames allowlisted in network_domains on the manifest.

Structural vs policy: Context shape, sandbox APIs, outbound fetch allowlists, and credential injection at the network layer are structural. Safety review, Developer Agreement terms, runtime anomaly review, and third-party API compliance are policy and contract — they complement structural enforcement rather than replace it.

2. Context minimization

When LUMARA invokes a SwarmSpace plugin, the full user context — CHRONICLE profile, journal-derived material, behavioral signals — is not passed wholesale to the plugin.

  1. LUMARA reads privacy_data_required from the plugin manifest.
  2. LUMARA extracts only those fields from the user context it holds locally.
  3. That subset is sent to SwarmSpace as part of the invocation.
  4. The Dynamic Worker sandbox receives only that subset in its context argument.
  5. Plugin code has no supported mechanism to request additional CHRONICLE fields mid-flight. Undeclared channels are outside the exposed API.

What the plugin receives — weather plugin (declares location only)

// privacy_data_required: ["location"]
{
  "query": "What's the weather like this afternoon?",
  "context": {
    "location": "San Diego, CA"
  },
  "metadata": {
    "caller": "lumara",
    "request_id": "7b2c9f1a-4e8d-4b3c-9f01-123456789abc",
    "tier": "free"
  }
}

The plugin does not receive the user's name, journal text, full CHRONICLE graph, or any undeclared field. Those values are never attached at the client minimization step and are not injected by the worker.

What the plugin receives — research plugin (declares no personal context)

// privacy_data_required: ["none"]
{
  "query": "Summarize recent papers on transformer scaling laws",
  "context": {},
  "metadata": {
    "caller": "lumara",
    "request_id": "9d0e5a33-1111-2222-3333-444455556666",
    "tier": "free"
  }
}

3. Sandbox enforcement

Each plugin call executes inside a Cloudflare Dynamic Worker V8 isolate. Each invocation runs in its own isolate with no shared mutable state between concurrent calls or between different plugins. Only platform-declared bindings and APIs are exposed — the plugin cannot import arbitrary modules, open raw sockets, or reach internal SwarmSpace services outside the published worker surface.

Network control: Default posture is globalOutbound: null. Outbound HTTP(S) is permitted only to origins whose hostnames appear in the manifest network_domains array. Fetches to other hosts are blocked at the platform layer, not only caught by review.

Credential injection: SwarmSpace holds secrets for third-party APIs and attaches authorization at the network boundary. Plugin code issues a standard fetch(); the API key is injected transparently. The raw secret is not exposed to plugin bytecode.

Runtime monitoring: Executions are observable. Outbound targets, volume, latency, and response shapes are compared to declared behavior. Anomalies feed logging and human or automated review. Monitoring is operational enforcement, not a substitute for the structural blocks.

4. Behavioral manifest fields

Three fields on your manifest determine how PRISM and the orchestrator treat your plugin in automated and chained execution contexts. Declare these accurately — they are verified during sandbox testing.

FieldMeaning
is_read_only Plugin only reads data. Does not write to external systems, send messages, or modify state. Read-only plugins auto-approve in scheduled auto execution mode.
is_destructive Plugin modifies, deletes, publishes, or sends data to external systems. Destructive plugins require explicit user confirmation even inside an already-approved workflow chain, and are blocked entirely in headless auto mode.
headless Plugin is designed to run without a user-facing confirmation step. Required for Durable Object dispatch. Verified tier only. Incompatible with is_destructive: true.

5. PRISM for recurring agents

Recurring agents running on Cloudflare Durable Objects follow a strict boundary on what may be stored versus what is fetched fresh at each execution.

  • Stored in the Durable Object: Last-run output snapshot (for delta computation), schedule configuration, alarm trigger metadata, run history needed to operate the schedule.
  • Not stored in the Durable Object: Full personal context, CHRONICLE payloads, behavioral models, journal entries, or other rich user state.

On each scheduled execution, the DO requests fresh context from LUMARA at run time, injects it into the workflow run, uses it for synthesis, then discards it. Personal context exists only for the duration of that execution path — it is not durably held in the DO as a user profile cache.

6. PRISM for catalogue discovery

When LUMARA calls SwarmSpace's proactive discovery endpoint (/catalogue/updates), interest tags are derived on the client from CHRONICLE and related local signals. SwarmSpace receives tag hashes, not raw CHRONICLE documents. With only hashed tags, SwarmSpace cannot reconstruct the user's full profile from that request. LUMARA performs additional relevance filtering using full local context before surfacing goal cards.

7. What PRISM does not do

Scope and honest limitations

  • Transport encryption — PRISM does not replace TLS. Traffic relies on HTTPS as normal.
  • End-to-end encryption of stored data — PRISM is not an E2EE store. Server-side encryption and E2EE are separate concerns.
  • User overrides — PRISM does not stop a user from voluntarily sharing more context when the product offers that control. Minimization is the default, not an absolute against user intent.
  • Third-party endpoints — PRISM does not audit how external APIs declared in network_domains handle data after the request leaves SwarmSpace. The Developer Agreement and vendor terms address this contractually.
  • Indirect prompt injection — Content returned from the open web or other untrusted sources fetched at runtime can still influence model behavior. Runtime monitoring, review, and agreements mitigate abuse; residual risk remains an industry-wide problem not fully solved by PRISM alone.

8. Developer obligations

  • Declare privacy_data_required honestly. Request only fields your implementation actually uses. Over-declaration is a safety-review failure.
  • Declare network_domains completely. Any hostname contacted during normal operation must appear. Undeclared egress is blocked structurally where the sandbox applies.
  • Avoid exfiltration side channels. Encoding user data into URLs or bodies to declared domains in ways that violate policy is a manifest honesty violation. Runtime monitoring targets such patterns.
  • Comply with the Developer Agreement. Including third-party API ToS and data handling clauses.
  • Do not retain user context beyond the API call unless explicitly declared, user-authorized, and approved through review.

Violations can result in rejection, de-listing, or account action regardless of technical minimization.
